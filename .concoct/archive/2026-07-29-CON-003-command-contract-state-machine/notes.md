## Implementation findings and decisions

- The task remains implementation-ready after repository inspection. The planned deliverables, acceptance criteria, and documentation-only boundary match the current repository; no product ambiguity requires escalation.
- The roadmap's `roadmapped`, `implemented`, and `reviewed` labels are useful journey projections but cannot be normative detected states. `roadmapped` overlaps `ready` because roadmap work can leave no active-task artifact, while `implemented` and `reviewed` omit task progress and review outcome needed to choose the next command.
- The normative model will therefore use mutually exclusive artifact-backed states: `uninitialized`, `ready`, `planned`, `implementation-in-progress`, `implementation-complete`, `review-changes-requested`, `review-approved`, `review-blocked`, and `invalid`. The compact roadmap labels will be documented as projections onto those states.
- Role commands have two observable moments: the CLI invocation validates state and emits deterministic handoff content without changing workflow artifacts; the selected role then performs the authorized work and establishes the resulting durable state. This distinction is necessary to remain compatible with deterministic prompt rendering and the later direct-agent-execution roadmap item.
- A latest completed review takes precedence over task status for actionable state, provided its sequence, metadata, and task identity are valid. Approval does not become archival readiness when capability impact or required archive inputs remain unresolved; such contradictions are `invalid` rather than a weaker workflow state.
- Deterministic remediation needs evidence newer and stronger than prose or file timestamps. The contract adds task-plan metadata `remediates-review`, which must name the exact latest `changes-requested` review while the Developer is addressing it; a completed remediation also requires dispositions for every finding in notes.
- `blocked` is a durable review outcome but has no universal next command. Recovery is a non-mutating handoff to the responsible persona or human, after which the existing role command may be used when the blocker is resolved.
